Introduction

How to Measure an Algorithm's Efficiency

A short review of the basics from Levitin §2.1–2.2. The modules cannot be read without it: everything that follows is counting one operation as a function of the input size.

Input size

Almost every algorithm runs longer on larger inputs. Therefore efficiency is expressed as a function of a parameter $n$, the input size.

  • Sorting, searching, finding the maximum of an array: $n$ is the number of elements.
  • Multiplying $n\times n$ matrices: usually the matrix order $n$. One could also take the number of elements $N = n^2$, but then the same algorithm gets a different class (see problem A3).
  • The input is a single number $n$ (primality testing): the size is the number of bits $$b = \lfloor \log_2 n \rfloor + 1.$$ The value of $n$ then grows exponentially in $b$.

Sometimes there are several parameters: for a graph, the number of vertices and the number of edges.

Basic operation

Measuring time in seconds is inconvenient: it depends on the computer, the compiler and the quality of the program. Instead, we choose the basic operation, the one that contributes the most to the running time, and count how many times it is executed. Usually it is the most time-consuming operation in the innermost loop: a key comparison in sorting and searching, a multiplication in matrix algorithms.

If $c_{op}$ is the execution time of one basic operation and $C(n)$ is the number of times it is executed, then

$$T(n) \approx c_{op}\, C(n).$$

The formula is approximate, but it lets us answer questions about ratios. Let $C(n) = \tfrac12 n(n-1) \approx \tfrac12 n^2$ for large $n$. How much longer will the algorithm run on an input twice as large?

$$\frac{T(2n)}{T(n)} \approx \frac{c_{op}\cdot\tfrac12(2n)^2}{c_{op}\cdot\tfrac12 n^2} = 4.$$

Both $c_{op}$ and the factor $\tfrac12$ cancel out. This is why the analysis ignores constant multiples and concentrates only on the order of growth.

Order of growth

On small inputs the difference between algorithms is barely visible. It shows up for large $n$, and it is determined by the order of growth of the function $C(n)$.

Algorithms with an exponential number of operations are practical only for very small inputs. An interactive chart is in Module 1.

The base of the logarithm does not affect the order of growth: $\log_a n = \log_a b \cdot \log_b n$ differs from $\log_b n$ by a constant multiple. That is why we simply write $\log n$.

O, Ω and Θ notations

Below, $t(n)$ is the number of operations of an algorithm and $g(n)$ is a simple function to compare with; both are nonnegative.

$O$ (upper bound). $t(n) \in O(g(n))$ if there exist $c > 0$ and $n_0 \ge 0$ such that $t(n) \le c\,g(n)$ for all $n \ge n_0$. More: O-notation.

$\Omega$ (lower bound). $t(n) \in \Omega(g(n))$ if $t(n) \ge c\,g(n)$ for all $n \ge n_0$ for some $c > 0$, $n_0$. More: Ω-notation.

$\Theta$ (tight bound). $t(n) \in \Theta(g(n))$ if $c_2\,g(n) \le t(n) \le c_1\,g(n)$ for all $n \ge n_0$. More: Θ-notation.

How not to mix them up: $O$ means “grows no faster”, $\Omega$ means “grows no slower”, $\Theta$ means “grows at the same rate”. $\Theta$ means $O$ and $\Omega$ at the same time. Example for $t(n) = 3n^2 + 5$:

$g(n) = n$$g(n) = n^2$$g(n) = n^3$
$t \in O(g)$?noyesyes
$t \in \Omega(g)$?yesyesno
$t \in \Theta(g)$?noyesno

So the statement $3n^2 + 5 \in O(n^3)$ is true but not very informative; the precise answer is $\Theta(n^2)$. In the worked examples we look for $\Theta$.

An example of a proof by definition: $\tfrac12 n(n-1) \in \Theta(n^2)$. Upper bound: $\tfrac12 n^2 - \tfrac12 n \le \tfrac12 n^2$ for $n \ge 0$. Lower bound: for $n \ge 2$ we have $\tfrac12 n \le \tfrac14 n^2$, hence $\tfrac12 n^2 - \tfrac12 n \ge \tfrac14 n^2$. The values $c_1 = \tfrac12$, $c_2 = \tfrac14$, $n_0 = 2$ work.

In practice it is more convenient to compare using a limit:

$$\lim_{n\to\infty}\frac{t(n)}{g(n)} = \begin{cases} 0 & t \text{ grows slower: } t \in O(g),\\ c > 0 & \text{same order: } t \in \Theta(g),\\ \infty & t \text{ grows faster: } t \in \Omega(g).\end{cases}$$

If an algorithm consists of two consecutively executed parts, its overall order is determined by the part with the higher order of growth:

$$t_1 \in O(g_1),\ t_2 \in O(g_2) \ \Rightarrow\ t_1 + t_2 \in O(\max\{g_1, g_2\}).$$

Worst, best and average cases

For many algorithms the number of operations depends not only on $n$ but also on the particular input. The classic example is sequential search for a key $K$:

ALGORITHM SequentialSearch(A[0..n − 1], K)
//Searches for K in an array; returns the index of the first match or −1
i ← 0
while i < n and A[i] ≠ K do
    i ← i + 1
if i < n return i
else return −1
  • Worst case: an input of size $n$ for which the number of operations is the largest. Here the key is absent or its first occurrence is in the last position: $C_{worst}(n) = n$. The worst-case efficiency is a guarantee: there will never be more than $n$ comparisons.
  • Best case: an input of size $n$ for which the number of operations is the smallest. Here the key is first: $C_{best}(n) = 1$. The best case is not a small input: the size $n$ is fixed, only the contents are chosen.
  • Average case: the expected number of operations on a “random” input. It requires explicit probabilistic assumptions. It is not equal to the arithmetic mean of the worst and best cases. The full derivation for sequential search is in Module 1.

If the number of operations is the same for all inputs of size $n$ (as when finding the maximum), the three cases coincide and are not distinguished.
